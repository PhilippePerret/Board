=== Définition des services ===

Il existe deux grandes catégories de services : 

- les <<custom-services, services personnalisés>>
- les <<common-services, services communs>>

[[custom-services, services personnalisés]]
==== Services personnalisés

On peut basculer des <<services communs>> aux custom-services grâce au bouton “Services communs”.

[[common-services, services communs]]
==== Services communs ====

Les services communs peuvent s'ajouter aux projets, mais ils peuvent aussi être cliqués dans la liste. Ils s'appliquent alors au projet courant.

On affiche les services communs simplement en cliquant sur la fiche d'un projet. En même temps qu'il se met en sélection, la liste des services communs s'affiche à droite de l'interface.

On peut basculer des <<custom-services>> aux services communs grâce au bouton “Services personnalisés”.

[[services-data, données des sercices]]
=== Données des services ===

[cols="1,4"]
|====
|`id`       | Identifiant du service
|           | Cet identifiant sert aussi à définir le nom du script à jouer (`mon-id-script` → `MonIdScript.scpt`) +
(les scripts sont définis dans `backend/scripts/`)
| `script`  | Si le script ne doit pas être déduit de l'identifiant
| `scType`  | Extension du script à jouer quand ça n'est pas `.scpt` +
(mais de toutes façons, il y a une recherche automatique du bon script en cas d'introuvabilité).
| `front`   | Propriété très importante qui définit **une méthode** frontend qui sera utilisée pour exécuter le service. Cf. <<exec-service-frontend>>.
|`name`     | Le nom affiché du service +
(pour les <<custom-services>>, ce nom est modifiable dès l'attribution.)
| `params`    | Les <<script-params>> (très importants, ils font l'objet d'un détail propre)
| `dynParams` | Beaucoup de services utilisent des paramètres à définir à l'utilisation du bouton. +
Ils fonctionnent essentiellement commes les <<script-params>>, mais les valeurs ne sont pas persistées (elles peuvent l'être, en étant <<service-fixable-dynparams, fixées>>).
|====

[[script-params, paramètres de script]]
==== Paramètres des script ====

Ils sont très important car ils définissent les paramètres exacts qui seront transmis aux scripts.

Principes : 

- Les valeurs paramètres sont transmis dans l'ordre exact où ils sont définis,
- chaque _paramètre_ peut définir plusieurs valeurs.

[cols="1,4"]
|====
| **Propriété**   | **Description**
| `id`        | Identifiant du paramètres (peut être répété dans les paramètres qui est un Array)
| `type`      | Le type précis qui va définir exactement la valeur transmise. Voir les <<params-types>>
| `values`    | Quand le `type` est `select`, pour définir les valeurs à proposer.
| `value`     | La valeur par défaut ou la valeur brute.
| `transient` | [Optionnel] Indique que la valeur du paramètre ne doit pas être enregistrée quand 1) c'est un service commun 2) qui est appelé depuis le panneau. +
Typiquement, c'est le cas par exemple du code à jouer dans la fenêtre de Terminal quand le service commun “Ouvir un Terminal au dossier” est cliqué depuis le panneau : il faut alors demander le code, mais ne pas l'enregistrer dans les `common_services_data` du projet.
|====

[[params-types, types de paramètres]]
==== Types de paramètres ====

Ils s'agit de la propriété `type` des <<script-params>>. _Ces types sont utiles dans le fichier `frontend/js/ServiceDefiner.js`_

[cols="1,4"]
|====
| **Type**        | **Description**
| `raw`           | Donnée brute fournie dans `value`
| `bounds`        | Pour obtenir les dimensions d'une fenêtre Finder
| `finder-window` |  Pour obtenir toutes les informations sur la fenêtre courante
| `path`          | Un chemin d'accès à n'importe quoi, fichier, dossier, script…
| `path-or-null`  | Chemin d'accès optionnel.
| `url`           | Une URL existante.
| `boolean`       | Soit false soit true
| `integer`       | Un entier
| `project`       | Une donnée projet déjà définie. L'identifiant est le nom de la propriété. Par exemple `path`
| `app`           | Une donnée application déjà définie. L'identifiant est le nom de la propriété. Par exemple `documentation-editor`
|====

[[exec-service-frontend]]
==== Exécution frontend d'un service ====

La plupart des services appellent un script qui se trouve backend (dont le nom est tiré de l'`id` du service ou définit explicitement par la propriété `script`). Mais certains services, comme l'horloge, font appel à une exécution essentiellement frontend (en tout cas jusqu'à l'enregistrement du temps et des changelogs/todo).

Pour caractériser ce genre de service, on définit dans leur <<services-data, données>> la propriété `front` qui sera la méthode (bindée) à appeler.

Cette méthode doit recevoir :

- le projet en premier argument,
- les données propres au service (`sdata[<service-id>]`) en second argument, comme une liste de valeurs.

[[service-dynamique-properties]]
==== Propriétés dynamiques ====

Les **propriétés dynamiques** des services sont des propriétés qui ne sont définies qu'à l'usage du bouton dans le projet (sauf si cette propriété est <<service-fixable-dynparams, fixée>>). 

Par exemple, si on ajoute à un projet le bouton « Créer un fichier », à chaque utilisation, le service va demander l'emplacement (le dossier) et le nom du fichier à créer.

[[service-fixable-dynparams]]
==== Propriétés fixables ====

Certaines <<service-dynamique-properties, propriétés dynamiques>> des services sont « fixables » ce qui permet d'obtenir encore plus d'efficacité, en prédéfinissant les propriétés des services.

Par exemple, si l'on reprend l'exemple du service « Créer un fichier », on peut le glisser sur un projet pour créer un bouton « Créer un fichier documentation » et **fixer** l'emplacement (le dossier) pour qu'il soit toujours le dossier documentation. De cette manière, lorsque l'on cliquera sur ce bouton, le service ne demandera que le nom du fichier, et le créera automatiquement dans le dossier.

Autre exemple. On peut imaginer trois boutons pour versionner un fichier : « Nouveau patch », « Nouvelle version mineure », « Nouvelle version majeure ». Pour chaque bouton, on définit les paramètres non dynamiques que sont 1) le fichier à versionner, 2) le dossier d'archive où mettre la version archivées. En ensuite, on fixe la **nature** de la version pour chaque bouton, « patch » pour le premier, « version mineure » pour le deuxième et « version majeure » pour le troisième.

De cette manière, chaque bouton peut avoir une portée large (aucune propriété dynamique **fixée**, avec nécessité de la redéfinir chaque fois) ou au contraire une portée très précise (avec un simple clic pour l'activer, sans avoir rien à définir).
