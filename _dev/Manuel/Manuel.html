Présentation

Cette application est pensée pour simplifier la gestion de l’installation du travail lorsqu’on développe plusieurs projets de front.

Elle se présent comme un panneau affichant chaque projet avec, pour chaque projet, un bouton permettant d’installer et de préparer le travail.

Cette instllation peut consister à :

  • ouvrir le dossier du projet dans le finder, dans une fenêtre personnalisée (taille, position, type de vue),

  • actualiser un fichier versionné et mettre l’ancien dans un dossier d’archives,

  • lancer un script qui va chercher une information sur le net,

  • ouvrir un fichier dans LibreOffice,

  • ouvrir un dossier de code dans VSCode,

  • et bien d’autres choses.

On appelle toutes ces opérations des services qu’on peut appliquer aux projets.

Prise en main

Après avoir lancé l’application, on se retrouve devant un tableau de bord qui permet d’ajouter ses projets en définissant pour chacun d’eux les Les services dont on a besoin.

Chaque projet se présente sous forme d’une carte (un peu comme dans Trello) qui possède en titre le nom du projet et contient la liste des différents services qui lui ont été affectés.

~ “Affecter des services” est l’expression consacrée pour dire qu’on utilise des Les services pour un projet. ~

Chaque carte est composée de trois parties :

  • l’entête, avec le titre du projet et quelques informations le concernant,

  • une partie supérieure contient tous les services qui seront activés lorsque l’on cliquera sur le bouton “Démarrer le travail”,

  • une partie inférieure contient les boutons qu’on peut utiliser à l’occasion pour des traitements particuliers.

Panneau de nouveau projet

Quand on clique sur le "+" qui se trouve à gauche en bas de l’interface, un panneau s’ouvre pour définir le nouveau projet.

La partie supérieure permet d’entrer les informations sur le projet :

  • lui donner un titre,

  • indiquer son dossier de référence (un projet doit toujours avoir un dossier),

La partie inférieure permet de choisir les Les services par simple glisser-déposer.

Exemple : pour le service “Ouvrir dans le Finder”, une fois qu’on l’a glissé sur le projet, une fenêtre s’ouvre, demandant d’ouvrir la fenêtre dans le Finder, de la positionner et de la mettre ans la vue désirée (colonnes, lignes, etc.). Une fois que c’est fait, on clique sur “OK” et l’application va automatiquement prendre les informations sur la fenêtre au premier plan dans le finder.

Todoist

Une autre force de Board est de pouvoir travailler avec l’application Todoist.

Il suffit de cliquer sur la petite icône pour avoir un accès direct à l’application pour :

  • lier le projet

  • créer le projet,

  • lire les tâches du jour,

  • créer de nouvelles tâches.

Lier le projet

Si le projet existe déjà dans Todoist, il suffit de le lier en cliquant une première fois sur le logo. Board demandera son titre (qui peut être différent du titre dans Board) et le retrouvera, s’il existe sous ce nom, dans Todoist.

Le projet dans Board sera alors automatiquement lié au projet dans Todois. Cela, concrètement, signifie qu’on peut :

  • voir au démarrage le nombre de tâches du jour,

  • marquer les tâches achevées,

  • créer de nouvelles tâches.

Les scripts-services

Les scripts-services offrent des possibilités infinies pour gérer ses projets. Ils permettent de composer soi-même un service complexe en exploitant toutes les ressources de l’application. Le tout premier script-service composé au moment de l’implémentation de cette application a permis de produire, avec un simple clic sur un bouton :

  • choisir une maison d’édition (ME),

  • ou en créer une nouvelle,

  • faire un dossier d’envoi pour cette ME, dans le dossier envois du projet,

  • choisir le manuscript courant s’il n’était pas déjà défini

  • dupliquer dans le dossier de la ME le manuscript courant à envoyer,

  • créer un fichier avec l’adresse et le téléphone de la ME,

  • incrémenter l’historique des envois en y ajoutant cet envoi, avec la date (différée ou non).

Tout cela, nous le redisons : par un simple clique sur un bouton.

ATTENTION: Tout pouvoir puissant, cependant, implique des responsabilités proportionnelles, comme nous le verrons. Il est donc conseillé d’avancer doucement dans la conception de ces scripts-services jusqu’à se sentir suffisamment à l’aise pour en composer des compliqués.

Une suite d’étapes

Un script-service est un fichier YAML qui décrit la suite procédurale des étapes du service. Concrètement, cela signifie que le fichier comporte des tirets pour délimiter chaque étape.

---
- name: Première étape
  id: 'etape-1

- name: Deuxième étape
  id: 'etape-2

- name: Troisième étape
  id: 'etape-3

# etc.

Pour illustrer l’explication qui va suivre, nous allons imaginer être une autrice ou un auteur et programmer un service de suivi d’envoi de manuscrits à des maisons d’édition, pour ne pas avoir à répéter un même processus des dizaines de fois, ce qui peut être pénible si l’on écrit un roman, voire plus, par an.

En apparence, ce service doit être simple :

  • création d’un dossier pour l’éditeur ou l’éditrice

  • copier du manuscrit à envoyer

  • création d’un fichier avec l’adresse et le téléphone de l’édition

  • enregistrement d’un historique des envois, pour se souvenir de quand le manuscrit a été envoyé.

Notre fichier YAML comprendra donc ces étapes, assurément :

---
- name: "Création du dossier de l'éditeur"

- name: "Copie du manuscrit envoyé"

- name: "Fichier information éditeur

- name: "Enregistrement envoi dans l'historique"

Noter que le name des étapes est optionnel, mais pour la clarté, il vaut mieux le définir.

En revanche, chaque étape doit impérativement avoir un identifiant (ìd). C’est une valeur ne comportant que des lettres minuscules, des chiffres, des tirets et des traits plats. Si l’identifiant contient des tirets, il doit obligatoirement être entre guillemets.

---
- name: "Création du dossier de l'éditeur"
  id: "creer-dossier-editeur"

- name: "Copie du manuscrit envoyé"
  id: copier_manuscrit

- name: "Fichier information éditeur
  id: informations_editeur

- name: "Enregistrement envoi dans l'historique"
  id: historique

Étape conditionnelle

On utile le paramètre if pour définir une étape conditionnelle.

La valeur de if doit alors être composée de 3 expressions séparées par une espace, la première étant la valeur a comparée, la 3e la valeur de comparaison et la 2e l’opérateur.

if: "expression operateur attendu"

expression est le plus souvent un identifiant d’étape exprimé par ${<id etape>}. On prendra alors la valeur de cette étape pour la comparer à expected.

operateur peut être == ou =, != ou ≠, >, <.

attendu peut-être n’importe quelle valeur, en sachant que "null", "undefined", "empty" seront évalués.
Quand le type est select et que create est à true (ou nom du bouton "Autre…"), autorisant la création d’une nouvelle valeur, expected doit alors être ''. Par exemple :

- id: 'value-selected-or-created'
  name: 'valeur à sélectionner ou créer'
  type: 'select'
  create: true

- if: "${value-selected-or-created} == ''
  type: 'string'
  title: "Nouvelle valeur
  q: "Donnez la nouvelle valeur.

Contenu évaluable

Dans les étapes, un contenu évaluable est un contenu qui se sert de la valeur d’une autre étape pour être défini.

Ce contenu s’indique par :

${step-id}          # Valeur de l'étape d'id +step-id+
${step-id}[prop]    # Si la valeur de l'étape *step-id+ est un objet, on
                    # prend la propriété +prop+ de cet objet.
${step-id}.prop     # Idem, sous une autre forme

Par exemple, on récupère un dossier et on s’en sert ensuite dans les étapes suivantes :

---
# On demande à l'utilisateur de choisir un dossier
- id: 'dossier'
  type: 'choose-folder'
  q: "Choisissez le dossier puis “OK”."

# On crée un fichier dans ce dossier.
- id: 'un-fichier-dans-le-dossier'
  type: 'add-to-file'
  # Le fichier estimé dans le dossier
  path: "${dossier}/mon_fichier.md"
  # Le contenu aussi peut s'en servir
  content: "Le contenu de mon fichier dans le dossier ${dossier}.

Les types d’étapes (step)

Dans cette longue partie nous allons voir et étudier tous les types d’étapes, donc les types de services utilisables dans les scripts-services.

Add-to-file

Ce type d’étape permet d’ajouter du contenu à un fichier.

---
- id: 'id-etape'
  type: 'add-to-file'
  path: "/chemin/vers/fichier
  content: ""
  after: "..."
  before: "..."
  where: [{after:...}, {before:...}, ...]

path

Chemin d’accès au fichier

Chemin absolu

Aucune substitution nécessaire

Chemin relatif

Doit se trouver dans le dossier du projet et commencer par "./"

Chemin évaluable

Se sert de la valeur d’autres étapes

content

Le contenu à écrire dans le fichier. Il peut être brut ou évaluable

after

Indique après quoi il faut mettre le contenu.

String

Ça peut être l’expression en chaine, p.e. "ce mot"

Exp. reg.

Ou une expression régulière. P.e. "(?!un ) voisin", pour mettre après "le voisin" mais pas "un voisin). Ces expressions demande de l’expérience.

before

Indique avant quoi il faut mettre le contenu. Mêmes formats que pour after.

where

Alors que after et before ne permettent qu’une localisation à un paramètre, where permet de définir très précisément où mettre le contenu. Mais cette définition est très sensible.

Voilà un exemple (absurde mais simple) : nous voulons ajouter ", cuisine" dans le contenu d’un fichier qui est pour le moment : "Je dois mettre au grenier un mot entre chambre et grenier."
Nous utilisons pour ce faire : `where = [{after: "chambre"}, {before: " et grenier"}]

De façon plus réaliste, sur cette base, on peut imaginer que le fichier contient des balises comme par exemple "/* — debut data — /" et "/ — fin data — /". Pour ajouter une donnée, on peut donc faire :
`where = [{after: "/ — debut data — /\n"}, {before: "\n/ — fin data — */"}]
Noter les retours de chariot marqués par "\n".

Translate

Permet de transposer une valeur par marqueur en vrai marqueur. L’exemple type de ces marques est la date today ou tomorrow qui sont automatiquement transposé en leur valeur réelle.

type

translate

 
---
- id: "id-de-step"
  type: translate
  value: "<valeur>"   # le marqueur (p.e. 'today', 'date+4'…)
  step: "<id step>"   # pour la prendre et la remettre dans l'étape
  format: "<format résultat optionnel>"

Si step est utilisé, c’est sa valeur qui est prise et remplacée. Noter qu’alors ce step remplace en même temps le paramètres valeur et set. La formule :

- id: transformation
  type: translate
  step: la-date
  format: '%J %_M

… est équivalent à :

- id: transformation
  type: translate
  value: "${la-date}"
  set: la-date
  format: '%J %_M

Les Formats de date

Les formats de date, utilisés pour transformation des valeurs ou le type translate, se définissent simplement par une chaine contenant des marqueurs qui seront remplacés par le valeur par rapport à la date fournie. Par exemple, dans la chaine "%J %_M", %J est un marqueur qui sera remplacé par le jour de la date (le 12 si nous sommes les 12 février 2026) et %_M est un autre marqueur qui ser remplacé par le mois en version nom ("février" pour la même date).

Liste des marqueurs

Explication

Exemples

%J

Le jour de la date

"1" ou "12"

%JJ

Le jour mais toujours sur 2 chiffres

"01" ou "12"

%M

Le mois de la date

"02" ou "11"

%_M

Le nom du mois de la date

"février"

%Y

L’année en 4 chiffres

"2026

%YY

L’année en 2 chiffres

"26"

%H

L’heure, en 1 ou 2 chiffres

"5"

%m

Les minutes, en 2 chiffres

"03"

%S

Les secondes en 2 chiffres

"06"

Si nous sommes le 25 juillet 2026 et que l’utilisateur choisit "Demain" pour l’étape suivante :

---
- id: date-chosen
  type: select
  values:[['today', "Aujourd'hui"],['demain', "Demain"]]
  q: "Quelle date choisissez-vous ?"

- id: la-date
  type: translate
  value: "${date-chosen}"
  transform: date
  format: "%_M, %Y le %J"

… alors la valeur de "${la-date}" sera mise à "juillet, 2026 le 26"

 Cette valeur est souvent réaffectée à l’étape select grâce à un type set. Voilà la séquence classique : 
---
- id: 'le-choix'
  type: select
  values: [1, 2, 3]
  q: "Choisissez un chiffre
  create: "Autre chiffre…" # pour permettre de choisir un autre chiffre

# Comme le choix "Autre…" a été choisi, on propose
# un dialogue pour entrer une autre valeur
# et, grâce à `set`, la donner à l'autre étape
- if: "${le-choix} == ''"
  id: 'autre-chiffre'
  type: string
  q: "Quel autre chiffre ?"

  transform: integer # tranformé en nombre

# À partir d'ici, l'étape ${le-choix} contient la valeur voulue,
# qu'elle est été prise dans le menu ou définie explicitement.

Données dans un fichier

On peut tirer des données d’un grand nombre de fichiers. La seule exigence est que la donnée remontée ait le même type que la donnée attendue (string, array, array de strings, etc.).

type

get-data

base

Chemin d’accès au fichier contenant les données (évaluable)

key

Si précisé, c’est la clé à prendre, qui deviendra la valeur de l’étape.
Si non précisé, c’est la liste des objets qui deviendra la valeur de l’étape.

Cela concerne donc en tout premier lieu les fichiers YAML, JSON et CSV, mais on peut également trouver tout fichier éditable (ruby, bash, python…) qui pourra retourner une donnée de ce type. Mais dans ce cas, il est impératif que ce fichier soit EXÉCUTABLE (chmod +x fichier) et qu’il retourne un données ÉVALUABLE PAR JSON, sauf si c’est une valeur scalaire (string, integer…).

Deux sortes de données peuvent être remontées :

  • une table (dict) dont une clé primaire correspondra à key,

  • une liste d’objet (array) qui devra contenir un élément répondant à id = key.

En réalité, je pense qu’on peut imaginer tout autre type de valeur aussi, puisque key peut ne pas être défini.

Création d’un objet complexe

La force des scripts-services est de pouvoir construire des objets complexes (avec plusieurs paramètres) à l’aide d’étapes successives pour pouvoir les enregistrer ensuite dans un fichier.

Nous présentons ci-dessous l’enregistrement d’un livre dans un fichier qui les liste.

# Définition préalable du chemin d'accès aux données du livre,
# pour ne pas avoir à les répéter (et pouvoir les modifier
# facilement)
- id: books-file
  type: set
  value: "./data/livres.yaml"

# Demande du livre qui appartient peut-être à la liste existante
- id: livre-id
  q: "Sélectionnez le livre à imprimer"
  select: "${books-file}"
  create: "Nouveau livre…" # pour en créer un nouveau

- if: "${livre-id} = ''"  # <= l'user a cliqué sur "Nouveau livre…"
  id: newlivre-titre   # id choisi avec soin (prefix-key)
  type: string
  q: "Titre du nouveau livre"

# Étape qui va tranformer le titre en identifiant valide
- if: "${livre-id} = ''"
  id: newlivre-id
  value: "${newlivre-titre}"
  transform: valid-id

- if: "${livre-id} = ''"
  id: newlivre-auteur
  q: "Auteur du livre :"
  type: string

- if: "${livre-id} = ''"
  id: newlivre-annee
  q: "Année de publication du livre :"
  type: string
  transform: integer

- if: "${livre-id} = ''"
  id: newlivre-resume
  q: "Résumé du livre :"
  type: text

# ... On pourrait ajouter encore des propriétés

# Cette étape va mettre dans ${new-book} l'objet du nouveau
# livre, qui pourra ensuite être enregistré
- if: "${livre-id} = ''"
  id: new-book
  type: save-data
  prefix: newlivre      # préfixe des étapes de définition
  values: ['titre', 'id', 'resume', 'auteur', 'annee']
  path: "${books-file}"  # L'objet sera placé dans ce fichier

# Il reste enfin à définir ${livre-id} qui sera utilisé par
# la suite
- if: "${livre-id} = ''"
  id: define-livre-id
  type: set
  step: livre-id
  value: "${newlivre-id}"


# À partir d'ici, on peut utiliser ${livre-id} pour obtenir
# l'identifiant du livre.

# On charge les données du livre
- id: book-data
  type: get-data
  base: "${books-file}"
  key:  "${livre-id}"

Utilisation des variables (valeur d’étape)

Dans un script-service, il est souvent utile de définir des variables et d’y faire référence.

Une variable, dans un script-service, est une valeur d’étape, on y fait référence par :

${<id d'étape>}
Tip
 Dans la suite, dès que nous parlerons de valeur d’étape il faudra donc comprendre qu’il s’agit de la valeur que prend l’étape au cours de son exécution ou la valeur qu’on lui définit explicitement.

Certaines variables se définissent en une seule fois, par exemple avec le type select :

- id: 'le-nombre'
  type: select
  values: [1,2,3,4,5]
  q: "Choisissez un nombre"

Avec cette étape, l’user choisira un nombre de 1 à 5 et ce nombre deviendra la valeur de l’étape le-nombre` et pourra donc être utilisé avec `${le-nombre}.

Par exemple pour une condition :

# Étape conditionnelle qui n'est jouée que le
# le nombre choisi est supérieur à 4
- if: "${le-nombre} > 4"
  id: etape-si-cinq
  ...

On peut également définir une variable explicitement grâce au type d’étape set. Si vous avez suivi, vous avez déjà compris que définir une variable revient à définir la valeur d’une étape. Si je joue :

- id: le-nombre
  type: set
  value: 3

… alors je mets explicitement la valeur de l’étape le-nombre à 3.

Utilisé de cette manière l’usage peut être limité, mais ça peut simplifier certaines écritures. Par exemple, si j’ai un nom assez complexe ou long, le mettre dans une variable peut être pratique :

- id: nom
  type: set
  value: "la Bhagavad-Gītā"

Je peux alors simplifier l’écriture des messages :

- id: version
  type: select
  q: "Quelle version de ${nom} dois-je prendre en référence ?
  values: [1,2,3]

Affectation plus complexe de variables

Les utilisations de variable précédents restent néanmoins simplistes et correspondent plutôt à l’utilisation de constantes que de véritables variables dont la valeur dépend en réalité du contexte.

Voyons comment utiliser une variable, par exemple, pour obtenir le titre du projet dans lequel est utilisé le script-service courant. Cette utilisation permet la portabilité complète des scripts-services, c’est-à-dire leur utilisation dans n’importe quel projet similaire (i.e. définissant les mêmes données).

- id: project-name
  type: get-project-data
  key: title

Grâce au type de service get-project-data, nous pouvons obtenir la propriété title (titre) du projet et la stocker en valeur de l’étape. On peut ensuite l’utiliser avec ${project-name} :

- id: pour-voir
  q: "Que voulez-vous faire de “${project-name}” ?"
  ...

À titre de rappel, les propriétés de base de tout projet sont title, id et path, mais on peut en ajouter autant que l’on veut notamment grâce au type set-project-data.

Nous pouvons aller encore plus loin dans l’affectation des variables et c’est même une nécessité pour de nombreux scripts-service. Cela se présente typiquement lorsque l’on veut que l’utilisateur puisse donner une valeur propre, c’est-à-dire autres que celles proposées. Vous vous souvenir de l’affectation d’un nombre, tout à l’heure, à la valeur d’une variable (la valeur de l’étape). Pour que l’user puisse utiliser sa propre valeur, il suffit de définir le paramètre create :

- id: le-nombre
  type: select
  values: [1,2,3,4,5]
  q: "Choisissez un nombre"
  create: "Autre valeur…"

Cette fois, l’user peut cliquer sur le bouton "Autre valeur…" pour donner sa valeur personnelle. Nous savons qu’il a cliqué sur le bouton car la valeur de ${le-nombre} sera vide. Nous la testons et lui proposons alors d’entrer sa valeur :

- if: "${le-nombre} = ''"
  id: autre-valeur
  type: string
  q: "Donnez votre propre valeur"
  translate: integer # pour transformer la chaine en nombre

Grâce à cette étape, l’user va pouvoir donner sa valeur.

Le problème, c’est qu’elle sera consignée dans ${autre-valeur} alors que plus tard, nous en aurons besoin dans ${le-nombre}. Pour ce faire, il nous suffit de définir le paramètre set avec le nom de l’autre étape :

- if: "${le-nombre} = ''"
  id: autre-valeur
  type: string
  q: "Donnez votre propre valeur"
  translate: integer # pour transformer la chaine en nombre
  set: le-nombre

Attention de ne pas affecter la valeur trop vite ! Prenons l’exemple d’une valeur que nous devons enregistrer dans le projet, pour ne pas avoir à la définir chaque fois que nous utilisons le script-service. Nous ne pouvons pas faire :

- if: "${le-nombre} = ''"
  id: autre-valeur
  type: string
  q: "Donnez votre propre valeur"
  transform: integer # pour transformer la chaine en nombre
  set: le-nombre

- if: "${le-nombre} = ''"
  id: save-nombre-in-project
  type: set-project-data
  value: "${le-nombre}"

Ça ne fonctionnerait pas parce qu’au moment de la ligne :

- if: "${le-nombre} = ''"

${le-nombre} ne sera plus vide puisqu’il aura été défini juste au-dessus (set: le-nombre qui signifie "définir la valeur de l’étape le-nombre avec la valeur de cette étape).

Il faut donc faire :

- if: "${le-nombre} = ''"
  id: autre-valeur
  type: string
  q: "Donnez votre propre valeur"
  transform: integer # pour transformer la chaine en nombre

- if: "${le-nombre} = ''"
  id: save-nombre-in-project
  type: set-project-data
  value: "${autre-valeur}"
  set: le-nombre

Exécution frontend d’un service

La plupart des services appellent un script qui se trouve backend (dont le nom est tiré de l'`id` du service ou définit explicitement par la propriété script). Mais certains services, comme l’horloge, font appel à une exécution essentiellement frontend (en tout cas jusqu’à l’enregistrement du temps et des changelogs/todo).

Pour caractériser ce genre de service, on définit dans leur données la propriété front qui sera la méthode (bindée) à appeler.

Cette méthode doit recevoir :

  • le projet en premier argument,

  • les données propres au service (sdata[<service-id>]) en second argument, comme une liste de valeurs.

Gérer les versions d’un fichier

On peut très facilement gérer les fichiers versionnés avec Board. On peut même choisir son système préféré :

AppleScript

Board fonctionne sur la base de nombreux scripts AppleScript pour commander les différentes applications.

Une librairie avec des méthodes utiles est implémentée dans backend/script/lib/Lib.scpt (c’est un exécutable qui ne peut pas être modifié, il faut modifier Lib-editable.scpt).

Pour pouvoir utiliser cette librairie dans n’importe quel script, il faut :

  • ajouter le nom de ce script dans OSASCRIPT_WITH_LIB dans `backend/lib/userfull.rb

  • ajouter en haut de son fichier :

on run argv set libPath to item 1 of argv set Lib to load script POSIX file libPath

...

Ou la version complète pour développement :

on run argv try set libPath to item 1 of argv set Lib to load script POSIX file libPath on error errMsg number errNum return "{\"ok\": false, \"error\":\"ERREUR CHARGEMENT LIBRAIRIE : " & errMsg & " avec " & libPath & "\"}" end try …​

  • la position et la taille

  • le type de vue

Backend

Tout comme le reste, le backend (backend.rb) est réduit à l’essentiel.

Pour l’exécution du service, rien n’est besoin d’être ajouté.

Pour la définition, il peut être nécessaire d’ajouter des scripts, mais beaucoup de choses peuvent être faite en utilisant l’action run-osascript ou run-bashscript pour jouer un script du dossier backend/scripts/

Paramètres fixes et paramètres dynamiques

Tous les services fonctionnent avec des paramètres fixes défines au moment de l’affectation d’un service à un projet. La première de ces paramètres fixes est le nom propre au projet du service. Par exemple, si le nom (name) du service est “Versionner un fichier”, le nom défini pour le projet par l’utilisateur au moment de l’affectation du service peut devenir “Versionner le manuscrit”.

Certains services nécessitent aussi des paramètres dynamique qui, elles, sont définies à la volée au moment de l’utilisation du service. Par exemple, au moment de versionner le manuscrit, Board va demander s’il faut incrémenter le numéro de path, de version mineur ou de version majeure.

Définition des paramètres fixes

Ces paramètres sont définis dans le fichier frontend/js/ServiceData.js. Si ces données sont modifiées, il faut lancer le script update.command à la racine de l’application.

Une définition ressemble à :

, params: [
    {id: 'window', q: null, value: null, type: 'finder-window', required: true},
    {id: 'sidebar', q: "Voulez-vous la sidebar ?", value: null, type: 'boolean', required: false}
  ]

id

fournit l’identifiant de l’élément DOM qui va contenir la valeur (#<id>.value)

q

définit la question qui sera posée à l’utilisateur pour définir le paramètre.

type

définit le type du champ d’édition(select, text-field, etc.). Voir tous les types de champ d’édition

Autres valeurs qui peuvent être définies en fonction du type`

values

définit les valeurs pour un menu select. Peut être [x, y, …] ou [[x, "nom x"], [y, "nom y"], …]

Ces paramètres doivent être définis dans l’ordre où ils seront consommés par le script backdend qui va les jouer.

Pour mémoire seulement, on peut les définir dans paramsOrder :

, paramsOrder: ['path', 'x', 'y', 'width', 'height', 'sidebar-width', 'type-view', 'show-sidebar']

Ils se définissent dans la propriété dynParams. Par exemple :

  ]

id

fournit l’identifiant de l’élément DOM qui va contenir la valeur (#__<id>.value)

q

définit la question qui sera posée à l’utilisateur.

type

définit le type d’interface (select, text-field, etc.).

Autres valeurs qui peuvent être définies en fonction du type`

values

définit les valeurs pour un menu select. Peut être [x, y, …] ou [[x, "nom x"], [y, "nom y"], …]

Comme pour les paramètres fixes, ces paramètres doivent être définis dans l’ordre où ils seront consommés par le script backdend qui va les jouer.

Script Backend

On appelle Script Backend le script placé dans le dossier backend/scripts/ qui va procéder à l’opération propre au service. Le script, par exemple, qui va changer la version du fichier.

Le nom du script ne peut pas être choisi au hasard, il correspond à l'`id` du service (par exemple "versionner-fichier") camelisé ("VersionnerFichier"). Son extension correspond bien entendu à son langage.

Dans ce script, qui peut être un script AppleScript, un script ruby, bash ou autre langage, les paramètres sont reçus à l’aveugle et en string.

À l’aveugle

Ils sont connus par leur ordre, sans aucune indication de ce qu’ils sont

En string

Toutes les valeurs sont des chaines de caractères, mais "true" ou "12".

Ordre des paramètres dans le script

L’ordre de réception des paramètres est celui défini par l’ordre des définitions des paramètres dans le fichier ServiceData.js. Le problème est que certains type de champ retourne plusieurs valeurs. C’est le cas typique, par exemple, pour le type finder-window qui retourne la position (2 valeurs), la taille (2 valeurs), le type de vue, etc. pour le seul paramètre window. Pour parlier ce problème, on peut renseigner la propriété d’aide paramsOrder avec l’ordre des paramètres.
